## Ticket feature plan (musonza/chat-backed, decisions confirmed: all users with the 'support' plan feature; closed tickets auto-reopen on customer reply)

### 1. Data model
- **Migration** `create_tickets_table`: `id`, `reference_number` (string, **unique** index), `subject` (string), `status` (string, TicketStatus enum: `open`/`answered`/`closed`, indexed), `user_id` (FK users), `conversation_id` (FK → musonza `mc_conversations`), timestamps. Real columns (filter/lookup needs), not JSON in conversation data. **File created only, NOT run** — you run `php artisan migrate`.
- **`app/Enums/TicketStatus.php`** — string-backed enum `Open`/`Answered`/`Closed` implementing `HasLabel` + `HasColor` (same pattern as `InvoiceStatus`/`CompanyReviewStatus`, labels translated, not Persian-hardcoded).
- **`app/Models/Ticket.php`** — `belongsTo(User)`, `belongsTo(Conversation)`, casts `status`. Status transitions as methods: staff reply → `answered`; staff closes → `closed`; user reply on closed → auto-reopen to `open` (confirmed rule).

### 2. Ticket creation + shared staff visibility (NO SupportTransferService)
- **`app/Services/Chat/TicketService.php`** — `create(User $user, string $subject, string $body): Ticket` inside a transaction:
  1. `Chat::createConversation([$user], ['type' => 'ticket'])` — a **private group conversation** (NOT `makeDirect()`), so no pair-uniqueness and all staff can join visibility without a random assignment;
  2. add the first message from the user;
  3. create the `Ticket` row with reference number;
  4. broadcast a new **`TicketCreated`** event (reuse `ChatConversationStarted`'s channel-naming helper `channelNameFor()`) on a private channel per staff user — actually simplest: since staff aren't participants yet, per-role fan-out like the fallback chain (`support`, `admin`, `super_admin` roles) each on their own user channel; authorization via `routes/channels.php` already handles `chat-participant.user.{id}`.
- **Staff visibility without participation:** the staff inbox queries `Ticket::whereIn('status', [...])` directly (tickets are first-class rows) rather than musonza participation lists. For message send/read inside a staff-opened thread, the claiming staff member is **added as an explicit conversation participant** on first reply (`$conversation->addParticipant($staff)`), following ChatParticipantResolver's explicit-participant model; reads use musonza's participant-independent message fetch guarded by the Ticket lookup (no direct-conversation pair constraints exist on private conversations).

### 3. Reference numbers
No existing sequential convention found (Invoice uses gateway refs). New: `TICKET-{YYYYMMDD}-{NNNN}` (per-day sequence from `where('reference_number','like',prefix)->count()+1`, created inside the ticket-creation transaction with a unique-index safety net).

### 4. User dashboard tab (`/tickets`)
- Route `Route::livewire('/tickets', 'pages::dashboard.tickets')->name('tickets')` in `routes/app.php` (no extra middleware — any authenticated user; feature gate checked in the page: `CompanySubscriptionService`-style feature check on 'support', all plans have it true).
- Nav: new `<li>` in `⚡infobar.blade.php` after the Chat tab, `menu.tickets` key, `request()->routeIs('tickets')` active check — exact same pattern as the Chat tab.
- **`pages/dashboard/⚡tickets.blade.php`** (new Livewire page): create form (subject + message), list of own tickets (reference, subject, status badge, updated_at), thread view reusing ⚡chat's message-presentation + Reverb listener patterns (listener on the ticket conversation's participant channel + fallback poll like ⚡chat).

### 5. Staff side — extend ⚡support-chats (no new UI)
Add a "tickets" section/tab inside `loadConversations()`: for staff (`hasAnyRole(support, admin, super_admin)`), load `Ticket` rows, present each with reference number + status badge + subject; opening a ticket thread reuses the existing conversation rendering. Staff reply adds them as participant, sets `answered`.

### 6. Translations — all five locale files
New `lang/*/tickets.php`: `title`, `create_title`, `subject`, `message`, `submit`, `reference`, `status_open/answered/closed`, `empty`, `staff_tab_title` + `menu.tickets` in `lang/*/menu.php`. Status enum labels reference `tickets.status_*`.

### 7. Notifications on new ticket
Broadcast `TicketCreated` (staff channels, per-user) — same infra as `ChatConversationStarted`; the staff inbox already does fallback polling so this is enhancement, not correctness-critical.

### 8. Tests (Feature, PHPUnit)
`TicketTest`: user creates ticket → reference format + conversation `data.type=ticket` + user is participant; staff of each role sees ticket in inbox query; staff reply adds participant + sets `answered`; user reply on `closed` reopens; non-owners/staff can't read others' tickets; ⚡tickets page renders list/form; support-chats surfaces ticket conversations.
